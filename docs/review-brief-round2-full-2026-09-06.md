## 2. 规则与评测链路（目标函数怎么运转）

### 2.1 平台侧固定件
- Add：平台逐 chunk 给消息(带 user_id/session_id/时间戳)；返回 200 前必须落库可搜。
- Search：平台给 query(+选项)，要求返回 ≤100 条证据；**由平台统一 Answer(gpt-4o-mini) 与 Judge**。
- Judge 判词要点(已核官方 pipeline)：typo 容忍；记忆冲突时 **prefer the most recent supported memory**；列表题要全项且 **no extras**；时间答案粒度严格、相对/绝对不可混。
- 维度：A 显式事实召回 / B 多跳组合 / C 时间与事件 / D 治理(含用户删除合规) / E 个性化 / G 上下文学习与执行 / H 认识论安全(拒答/最小披露)。
- 红线：隔离(user_id 精确)、评测数据 30 天删除、评测内容不留日志、禁跨样本共享状态、禁硬编码公开题、学术榜代码审查。

### 2.2 这给我们推导出的"可动空间"
1. **Search 输出只有两个自由度：返回哪些证据 + 什么顺序**。top1 决定 Hit@1；判官"取最新支持记忆"意味着**顺序中的时间结构本身可能是答案的一部分**。
2. **内部计算预算自选**：官方按 Slow/Medium/Fast 标注，Accuracy 榜独立——慢档不是禁止项(ReFind #2 即慢档)。
3. **滚动窗口 = 带真实反馈的闭环**：每轮提交拿私有回执 → 可做"假设→回执→维度失败归因→单变量改动→重交"。
4. 会话内(同一 conversation 内)状态未被明示禁止；跨样本共享状态被禁止。

### 2.3 我们踩过的规则坑（经验之一）
- 初版契约按旧版 api-guide 实现(scope/memory/timestamp/TopK90)，官方现行规范是 user_id/data/content/created_at/TopK100——**契约迁移要全链路(HTTP+存储+测试+文档)一起改**，中途我们出现过消费方残留。
- 曾把"本地评测 hit@1 0.909"当作重要数字，后确认与官方分**不可比**；现在所有数字都带口径标签。

## 3. 已具备能力（分层，含在评测链路中的作用）

### 3.1 契约/合规层（作用：过 Smoke/不扣合规分）
- golden 契约测试 + 官方 contract 测试；user_id 精确隔离(WAL/FTS/向量/缺席闸)；eval 日志脱敏 + 30 天 TTL；/health 自证(scene/journal/api_key/适配器/p95)；启动非参赛口径 WARN。
- 压测基线(stress_smoke, 1200 条)：add p95≈108ms、search p95≈10ms——单机红线内。

### 3.2 检索默认层（作用：给 Answer 喂 top 证据）
- fts(bigram, 中英) + hash 向量 双路 → RRF(k=60) 融合；RULE 通道 no_decay+boost；章节编号通道；FSRS 保留度调制(**首测中性**：官方第一轮无复习史→零贡献，仅真实使用有意义)；缺席闸(O(1) 判不在)；options 拼接查询(选项实体参与召回)。
- 本地证据：LME-S 21 题 top5 hash 命中 12/21(hit@1=4)；search 极快、确定性、离线。

### 3.3 治理层（作用：D 维度 + 防陈旧/防误杀）
- 治理 v2：词边界信号(不再把 now 当 know 里的子串)、问句/未来打算不触发、属性槽区分——真实误藏案例 2/21 修复归零；supersede/retcon 全审计链；soft 档(旧值降权保留) 与内容驱动 forget(R3，用户说删除即 FORGOTTEN) 就绪。

### 3.4 评测工具链（作用：让每次改动可复现、可对账）
- 本地回放器(provider/top_k/治理软硬/plan/expand/token-cap/rewrites 开关矩阵)；LongMemEval-S 与 InMind 转换器；recall_miss 逐题失败卡；质量闸(retrieval-gate，检索分掉>2% 即红，A 面 paraphrase 0.544 回归锚)；judge_v1 判答夹具(待 key)。

### 3.5 默认关实验件（全部带开关+测试，未进默认路径）
- 会话级 RRF(H1)、确定性查询规划(J1)、相对时间解析(F2)、年份过滤(R4)、年龄衰减(R1)、**读时 recency 仲裁(RAR)**、soft-supersede(B2)、邻接扩写(B1 填余量版)。

## 4. 经验教训（防止评审重复我们的路）

### 4.1 已证伪/已饱和——请不要再建议"试一下"
- RRF 权重档(词法 0.5 vs 等权)：本地 21 题逐项一致 → 中性。
- 长消息切块 320/40：召回略降(-1 hit)、token 省 20% → 不划算。
- 朴素语义(minilm)并入 RRF：top1 变 0 → 需要门控而非平等融合。
- 实体通道/语义默认开：小说与本地 A/B 零增益 → 维持关。
- 证据图/关系图：两代(P3 与官方案例)均负 → 不建。
- 门控"交换 top1/top2"：CHM P5 四类廉价信号全失败 → 不碰交换类门控。
- 集合感知重排(P2)、覆盖率/结构复杂度作为卖点 → 负结果。

### 4.2 教训：什么被证明是"叙事税"（别当成提分资产）
- FSRS/巩固/遗忘曲线/再巩固等生物启发机制：我们审计后定性为**真实使用与工程成熟度资产，官方首轮提分贡献=0**(首测中性是最硬证据)。
- Dreaming Cycle/完整 RARE/衰减引擎：未实现，只有设计稿 → 不是能力。
- 数学公理/维度地板/一致性审计：正确性护栏(防丢分)，不产生增益。
- **教训**：联想(生物/类比)只作为假设来源，必须收敛成"不依赖 key/数据的工程不变量+固定判官下有可证伪预测"才算有用；否则就是叙事。我们已按此把仿真层从参赛提分叙事中剥离。

### 4.3 教训：方法/工程层
- FSRS touch 让 Search **有状态**(跨题排序漂移)——滚动多轮私评对比会被污染，参赛档倾向关 touch。
- 弱加成型"微调"不足以改变排序结果(踩过：bonus 被 sort 覆盖) → 重排类机制必须在排序后、截断前显式执行。
- 默认关纪律：任何检索行为改动先成对实验+质量闸复跑；默认路径零变化(现 10+ 旋钮全部默认关)。
- 契约/规则先冻结再动代码；golden 单点收敛。
- 所有"本地分"必须带口径标签，防止把代理指标当官方分。

### 4.4 我们已建立的"测量边界"
- 检索侧证据召回(分桶 hit/fusion-miss/channel-miss/absent)已可测；
- **判答层未接入**(无 key)——所有"这个改动会不会提官方分"的问题当前都无法用答案正确性回答，只能用检索代理近似。

## 5. 已测弱点（这是最需要外部想法的起点）
- A 面释义召回：InMind direct 仅 54.4%(hash)/52%(minilm)——**同义改写类问题直接失分**。
- 间接/路由召回：indirect 20.8%/13.6%——问法语义不相关时决定性记忆根本进不了上下文(InMind 证实这是路由问题，非存储/模型问题)。
- C 时序：相对时间表述(几个月前/去年)召回失败复发——开放榜 C 整体只有 18-24.6，工业榜 56-60，说明同一判官下时序可被系统做高，但检索派普遍没做对。
- 本地语料限制：自述式、单会话、专名少 → 多个旋钮在本地不可分；需要多题/会话语料或官方数据才能裁决。

## 6. 现在要解决的决策点（Q1–Q7，请围绕这些给帮助）

### Q1 读时状态仲裁该不该进默认（我们倾向"做，先成对"）
- 现状：写入期硬隐藏(治理 v2，防陈旧但曾误藏)；AMI 用"零治理+全保留+时间戳"拿 D 第一(37.95)。
- 已做原型(RAR)：不删旧，检索时冲突簇(同 subject+共享词/实体)按 event_ts 显式把最新排前，旧态作支撑——与判官 prefer most recent 同构。
- 卡点：(a) 免解析/免模型的冲突键怎么更稳？(b) 新旧并存会不会害列表题 no-extras？(c) "当前态+历史支撑"在 token 预算下的最优配比(TREC 250→50 字节先例)？
- 想要的帮助：反例、冲突检测文献、列表题的量化风险实验设计。

### Q2 A 面释义/路由：在"固定稠密对所有人一样"下还能做什么
- 现状：默认 hash 词法；minilm 朴素并入伤 top1；查询改写需 LLM(Search 预算外)；会话内访问层学习(再巩固)有 gaming 风险、倾向放弃。
- 卡点：有没有不依赖模型、不依赖固定稠密差异、且不碰红线的释义/路由手段？查询历史的合法用法边界在哪？
- 想要的帮助：轻量词形/typo 处理是否值得进默认、检索派未见过的释义机制、对 gaming 风险的规则解读。

### Q3 C 时序：检索派内部破 C 的最小可靠件是什么
- 现状：event_ts 有；F2 相对→绝对解析器就绪(月≈30/年≈365)；年龄衰减/年份过滤默认关；判官时间粒度严格。
- 卡点：纯 Python 日历锚定够不够？事件顺序题是否需要"顺序索引"类结构而非检索排序？
- 想要的帮助：判官对时间答案的实际裁决案例、检索派做时间的高分做法、顺序类题的数据结构建议。

### Q4 滚动窗口多轮私评：闭环方法学
- 现状：计划"假设→回执→维度失败归因→单变量→重交"。
- 卡点：多轮调优在私有回执上的过拟合/多重比较风险；题集每轮是否相同未知；少轮次怎么信息最大化。
- 想要的帮助：评估学实践(如多次提交方差、变化量显著阈值)、主动实验设计。

### Q5 延迟-准确预算档：要不要学 ReFind 慢档换准确
- 现状：默认 10ms；官方按 Slow/Medium/Fast 标注、Accuracy 榜独立；P5 证明廉价信号"交换 top"不可靠。
- 卡点：确定性"追加召回"门控(低流畅/完整性词/时间标记→第二遍)是否值得做；还有哪些不依赖 LLM 的深检触发信号；慢档在官评的隐性代价证据。
- 想要的帮助：确定性深检触发设计、慢档榜的实证数据。

### Q6 无 key 阶段判答近似
- 现状：judge_v1 夹具就绪，需 OPENAI key 才能跑。
- 卡点：可信的开源判答/判官替代与官方 gpt-4o-mini 的一致性经验？样本量多小够当开关裁决？
- 想要的帮助：替代 judge 的一致性评测方法、最小样本量经验。

### Q7 工程与规模（自托管边界）
- 现状：SQLite+FTS5+内存向量；官方约 150M 字符量级；单机 Docker。
- 卡点：该量级 FTS/向量/治理全扫的拐点；是否值得换 sqlite-vec/独立 BM25 等自托管件；默认关旋钮 10+ 的发布面治理。
- 想要的帮助：规模测试设计、自托管件经验、配置面治理最佳实践。
